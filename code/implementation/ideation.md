To implement this cleanly for **article-like documents** (academic papers, technical blogs, essays, thinkpieces), treat the system as one conversational agent that is always trying to help the user think, but internally runs two coupled processes: a **stage controller** (Discovery → Conclusion) that changes how Z speaks, and a **scribe** that continuously extracts and organizes **Key Points (KPs)** into a mindmap-like IG with evidence. The “article” family is similar enough that you can share one dialogue architecture and one KP schema, then add an “academic lens” on top that cares about your 1–6 coverage, while a blog lens cares about thesis/argument/audience, etc.

In the **Discovery stage**, Z’s job is to maximize idea throughput and insight without interrogating the user. Z should feel like a smart collaborator: it reflects what it hears, suggests angles, and asks questions only when they help the user clarify their own thinking, not to satisfy an internal checklist. Practically, this means you bias toward responses that: restate the user’s idea in one sentence occasionally (to ground), highlight implications or tradeoffs, and offer optional directions (“we could explore X or Y next”) instead of asking a chain of questions. The stage controller should assume the user is still exploring unless there are clear signals of convergence. While in Discovery, the scribe is still extracting KPs, but it should be conservative about “locking” them: it can add KPs with a lower confidence when the user is brainstorming, and increase confidence only when the user repeats, corrects, or decides.

The **Conclusion stage** begins when the system believes the user is wrapping up exploration and is ready to shape the document. This isn’t a hard switch triggered by time; it’s triggered by conversational signals. You can implement this as a simple state machine with a continuous “convergence score.” Increase the convergence score when the user uses decisive language (“so the main point is…”, “I’ll focus on…”, “let’s settle on…”, “I think that’s enough”), when the novelty rate drops (fewer new distinct concepts per turn), when they start asking to package the idea (“summarize”, “outline”, “what should the paper contain”), or when they respond positively to Z’s synthesis (“yes exactly”). Decrease it when the user introduces brand new branches, uses hedging language (“maybe we should also…”) repeatedly, or explicitly says they’re still exploring. When the convergence score crosses a threshold, Z gradually becomes more direct: it starts proposing a crisp framing of what the article will be, surfaces the most central KPs, and asks a small number of clarifying questions only about things that are missing and materially affect the document. In Conclusion, Z should avoid re-asking anything the user already answered; instead it should phrase questions as “to lock this down” or “to make the article sharp,” and limit itself to one or two clarifiers at a time.

The most important behavioral detail is that Z should not ask “should I save X?” or expose the mechanics of KP capture. Z is the expert scribe. It silently decides what to store based on what the user said and how the user reacted. This means your KP extraction must be designed around **endorsement** rather than “who said it.” A key point can originate from either user or assistant, but it is only considered “accepted” when the user signals adoption. Adoption signals include: explicit assertions (“my goal is…”, “the core idea is…”), explicit confirmation of Z’s restatement (“yes, correct”), selection between options (“let’s use option B”), and user corrections (“no, change it to…”). When the assistant suggests something and the user doesn’t adopt it, it can remain as a “candidate” or be dropped. This is how you keep the IG trustworthy without interrupting flow.

For article-like documents, KP extraction should focus on units that actually shape writing. At minimum, KPs should include: the central thesis/idea, target audience and intent (inform/persuade/introduce), scope boundaries and constraints, key claims or arguments, important examples/analogies, comparisons to other approaches (especially academic), explicit questions the article answers (or the research questions), and the approach or method (for academic, also evaluation). The easiest way to make this work across article sub-genres is to store KPs in a small, stable set of types that are useful everywhere: “Goal”, “Thesis”, “Claim”, “Constraint”, “Definition”, “Question”, “Approach”, “Evidence/Reference”, “Example”, and “Decision.” For academic, you additionally track coverage of your 1–6 by tagging each KP, but you still store them using the same core types so the engine stays clean.

Implementation-wise, you’ll get the best results if you treat KP extraction as an internal structured output produced on every turn. After each user message, call the model in “scribe mode” with (a) the recent transcript window plus (b) a compact representation of the current accepted KPs. Ask it to output only JSON containing: new KPs to add, existing KPs to strengthen (increase confidence), existing KPs to revise/supersede, and edges between KPs that express relationships like supports, depends-on, contrasts-with, or elaborates. Require every KP to include evidence pointers to message IDs so you can always justify why it exists. When something is corrected, don’t overwrite; supersede it and keep history so the UI can later show previous alternatives. This is crucial for ideation because users often want to revisit earlier framings.

The relationship between the two-stage dialogue and KP extraction is where you can get real leverage. In Discovery, the scribe can allow more candidate KPs, but keep their confidence lower and avoid prematurely organizing them into a rigid spine. In Conclusion, Z should actively use the existing KPs to converge: it should synthesize a “document spine” from the highest-confidence KPs, narrow down which claims are central versus peripheral, and then ask clarifying questions specifically to resolve low-confidence but central items. Put differently: Discovery grows the map; Conclusion prunes and solidifies it. This is also where academic-specific coverage comes in: in Conclusion for academic, Z should look at which of the 1–6 aspects are missing from accepted KPs and choose the smallest set of natural questions that would fill the gap (often Distinction and Question), without making it feel like a template.

To keep the conversation smooth, implement a rule that Z asks clarifying questions sparingly in Discovery and more purposefully in Conclusion. In Discovery, questions are primarily to resolve ambiguity that blocks understanding, or to offer a useful fork that helps exploration. In Conclusion, questions are to lock the goal and shape: “what’s your intended contribution,” “what’s the closest baseline,” “what’s your primary research question,” “what constraints are you assuming,” phrased as minimal and contextual rather than as a checklist. The stage controller should also allow reversals: if the user re-enters exploration mode during Conclusion by introducing major new branches, Z should soften back toward Discovery rather than forcing convergence.

Finally, build a minimal “lens” abstraction now even though you’re focusing on articles. The lens does not make the system generic; it just keeps you from hardcoding academic assumptions into the core. The lens defines: which KP types are emphasized, which coverage dimensions matter, and which concluding questions are “must-have.”

academic uses 1–6:
1. **Clarification** — what the idea is about (core concept, scope, what you mean by key terms)
2. **Exploration** — what other relevant ideas/work exist (related work, adjacent approaches, baselines)
3. **Conception** — the set of ideas under constraints (assumptions, scope boundaries, constraints, what you will/won’t consider)
4. **Distinction** — how your concept differs from established concepts (novelty, differentiators, what’s new)
5. **Question** — the specific questions to answer (research questions / hypotheses)
6. **Approach** — how the research will answer them (method, evaluation plan at a high level)

blog uses: 
1. Thesis: the central claim you want the reader to walk away believing.
2. Audience: who you’re writing for (and what they already know), which determines tone, depth, 
3. Argument: the structured reasoning that persuades the audience to accept the thesis—usually a sequence of key points with evidence, counterpoints, and conclusion.

With this, you can start with an “AcademicArticleLens” and later add “TechnicalBlogLens” without rewriting dialogue or the KP engine.
